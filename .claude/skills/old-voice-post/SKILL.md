# old-voice-post

목표: 새 글을 쓸 때 2026년 글들(AI 티 나는 문체)이 아니라 2023년 이전 글들의 원래 말투로 쓴다.

## 1. 매번 다시 읽을 것 (캐시된 기억 쓰지 말기)

스타일 기준 소스는 아래 5개뿐이다. 최근 글(2026-*)은 스타일 참고에서 제외한다.

- `_posts/2023-07-20-LeanAndExec.md`
- `_posts/2023-07-21-git.md`
- `_posts/2023-07-28-docker.md`
- `_posts/2023-09-08-Put-Vs-Patch.md`
- `_posts/2023-09-12-jest-mocking.md`

새 글을 쓰기 전에 이 중 2~3개를 Read로 실제로 읽는다. 아래 체크리스트는 참고용 요약이지 대체재가 아니다.

## 2. 이 사람 말투 특징

- 동기가 항상 한 줄로 먼저 나온다: "~하다가 궁금해져서/헷갈려서 공부(정리)하게 되었다" 같은 문장으로 시작. 후킹 문구나 인용구로 안 연다.
- 문장 종결이 안 통일되어 있다. `-다`체와 `-습니다`체가 글 안에서 섞여도 그냥 둔다. 억지로 통일하지 않는다.
- 근거를 링크로 바로 붙인다: `[공식문서](...)`, `[참고한 블로그](...)` 를 소제목 밑에 그냥 나열. 각주 시스템 안 씀.
- 생각의 흐름을 `→`로 이어서 한 문단 안에 풀어쓴다 (docker 글 참고). 번호 매긴 리스트로 딱딱하게 안 쪼갠다.
- 표(table)는 개념 비교할 때 씀 (CRUD/HTTP 메서드 표 등). 화려한 표는 아니고 딱 필요한 것만.
- 확신 없는 부분은 확신 없다고 그대로 쓴다: "~것 같다", "~하지 않았을까 싶다", "~인 듯". 모든 문장을 단정적으로 안 만든다.
- 제목은 그냥 명사형이다: "GIT", "Docker란?", "Put Vs Patch". 콜론(:)이나 대시(—)로 부제 붙여서 "왜 중요한가", "실제로는 어떤 의미인가" 식으로 안 늘인다.
- `code` 백틱은 기술 용어/함수명에 바로바로 씀. 코드 블록은 실제 필요할 때만.

## 3. 절대 하지 말 것 (2026년 글들에서 생긴 AI 티)

2026-* 글들과 비교해서 다음은 빼야 한다:

- 제목에 em dash(—)나 콜론으로 부제 달아서 의미 설명하는 것
- 본문 시작을 따옴표 인용구("...")로 여는 후킹 오프닝
- `---` 구분선으로 섹션을 깔끔하게 나누는 것 (원래 글들은 `##` 소제목만 쓰고 구분선 남발 안 함)
- "1. **보안**: ...", "2. **확장성**: ..." 처럼 볼드 라벨 + 콜론으로 정리된 목록
- 마지막에 "정리하자면", "결론적으로" 하고 요약 섹션 따로 만드는 것
- 지나치게 매끈하게 다듬어진, 흠 하나 없는 문장 흐름. 약간 거칠어도 그대로 둔다.

## 4. 절차

1. 주제와 (있다면) 참고 자료를 받는다.
2. 위 5개 중 2~3개를 Read로 읽어서 문체를 다시 캘리브레이션한다.
3. 초안을 쓴다. frontmatter는 옛날 글 형식 그대로: `title`, `layout: post` 만 (date 필드 넣지 않음, 파일명 날짜로 대체).
4. 파일명은 `_posts/YYYY-MM-DD-slug.md` (오늘 날짜, 영문 slug).
5. 쓰고 나서 3절 금지 목록에 걸리는 게 있는지 스스로 훑고 걸리면 고친다.
