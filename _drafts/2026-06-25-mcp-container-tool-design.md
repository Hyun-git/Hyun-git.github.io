담당하던 IDE 플랫폼에서 채팅으로 자연어 명령을 하면 실제로 컨테이너 설정이 바뀌는 기능을 만들어야 하는 상황이 생겨서 MCP(Model Context Protocol) 기반으로 설계를 진행하게 되었다.

## 프로토타입부터

- [Model Context Protocol 공식 문서](https://modelcontextprotocol.io/)

처음에는 프로토타입 수준으로 시작했다. MCP 서버 하나를 붙여서 채팅 UI에서 질문을 하면 서버가 가진 기능(command) 중 하나가 실행되고 결과가 채팅창에 나오는 구조. 서버 연결이 되어야 채팅 입력이 활성화되고, 끊기면 재연결하는 정도의 흐름만 우선 잡았다.

시연 시나리오로는 "bear.lee의 컨테이너 보여줘", "bear.lee의 크레딧 보여줘" 같은 질문을 던지면 채팅 UI → mcp client → mcp server → 실제 백엔드 API 순으로 요청이 흘러가고, 응답이 다시 채팅창까지 돌아오는 걸 확인하는 정도로 짰다. 크레딧 예상 사용량 계산처럼 서버 쪽에서 약간의 연산을 거쳐 답을 만들어주는 케이스도 넣었는데, 여기서 자연어 질문 하나가 실제 도구 호출과 계산으로 이어진다는 걸 눈으로 보고 나니 방향이 맞겠다 싶었다.

## Tool 명세를 하나씩 쌓아가기

프로토타입 다음 단계는 실제로 쓸 Tool들을 하나씩 정의하는 일이었다. 컨테이너 상세 조회부터 시작해서 스펙 변경, 스토리지 변경, URL/포트 관리, 환경변수 관리, 초기화 스크립트 변경까지 — 컨테이너 관리 콘솔에서 사람이 클릭으로 하던 작업들을 하나씩 Tool로 옮기는 작업이었다.

각 Tool마다 `projectName`, `action`, `updateStatus` 같은 args를 정의하고 required/optional을 구분해두었는데, 이게 은근히 손이 많이 갔다. 예를 들어 컨테이너 advanced 설정(autoStop, AI 서포터, 코드 서포터) 변경은 하나의 Tool로 묶었지만 스펙 변경과 스토리지 변경은 각각 별도 Tool로 뺐다. 스펙은 컨테이너가 정지된 상태에서만 바꿀 수 있고 스토리지는 활성화되어 있으면서 정지된 상태에서만 가능한 등 제약 조건이 Tool마다 달라서 하나로 합치면 오히려 LLM이 판단하기 어려워질 것 같았기 때문.

에러 케이스도 같이 정리했다. 컨테이너 이름이 정확히 매칭되지 않으면 컨테이너 목록을 대신 반환하도록 하고, 이미 같은 상태로 업데이트를 시도하는 경우는 어떻게 처리할지 등은 팀에서 계속 논의가 필요한 부분으로 남겨뒀다.

## MCP ↔ 백엔드 응답 형식 표준화

Tool이 늘어나면서 각 Tool마다 응답 형식이 제각각이면 다루기 어려워질 게 뻔해서 공통 포맷을 먼저 잡았다.

```
{
  userQuery: string,
  tool: tool_type,
  result: stringify,
}
```

여기에 각 API의 Request Body / Response 스펙을 REST 엔드포인트 단위로 정리했다. `PATCH /api/mcp/users/:userId/projects/:projectName/spec` 같은 식으로 엔드포인트를 나누고, 응답에는 항상 `prevStatus`와 `afterStatus`를 같이 넣어서 뭐가 어떻게 바뀌었는지 명확히 드러나게 했다. 변경 전/후 값을 같이 반환하게 만든 게 나중에 확인 절차를 설계할 때 꽤 유용했다.

## 실행 전 한 번 더 확인하는 구조

여기서 제일 고민이 컸던 부분이다. AI가 컨테이너 스토리지를 삭제하거나 컨테이너를 정지시키는 것처럼 되돌리기 어려운 변경을 사용자 확인 없이 바로 실행해버리면 곤란하다. 그렇다고 매 Tool마다 확인 로직을 따로 박아넣으면 일관성이 없어질 것 같았다.

찾아본 방식 중 하나는 Tool을 두 단계로 나누는 것이었다. LLM이 먼저 "이렇게 바꾸겠습니다"라는 제안만 만들어내는 Tool을 호출하고, 사용자가 승인했을 때만 실제로 반영하는 Tool이 따로 실행되는 구조. 다른 방식으로는 하나의 Tool 호출에 `confirm` 같은 플래그를 넣어서, 처음엔 `confirm: false`로 호출해 변경 내용과 위험도(riskLevel)만 돌려받고, 사용자가 동의하면 `confirm: true`로 같은 요청을 다시 보내 실제 실행까지 이어지게 하는 것도 있었다. 참고했던 사례 중에는 위험도가 일정 수준 이상이면 자동으로 승인 절차를 거치도록 서버별 정책을 설정할 수 있게 만든 곳도 있었다.

결국 우리 쪽은 변경을 제안하는 단계와 실제로 적용하는 단계를 분리하는 쪽으로 방향을 잡았다. LLM이 직접 실행 권한을 갖는 대신 항상 사람의 확인을 한 번 거치도록 만들어야 안전하다는 결론이었다.

## 아키텍처 리서치 — LLM이 너무 많은 걸 맡고 있었다

- [LangChain and MCP: Building Enterprise AI Workflows with Universal Tool Integration](https://medium.com/@richardhightower/langchain-and-mcp-building-enterprise-ai-workflows-with-universal-tool-integration-e0547742233f)

구조를 잡아가면서 다시 들여다보니 문제가 하나 보였다. mcp client 쪽에 LLM이 붙어서 어떤 도구를 쓸지 판단하는 것과, 도구 호출 결과가 적절한지 판단하는 것을 동시에 맡고 있었다. 세션도 사용자 단위가 아니라 앱 단위로 유지되고 있어서 여러 사용자가 섞이면 문제가 될 여지도 있었고.

→ 도구 판단과 응답 판단을 한 곳에서 처리하다 보니 책임이 불분명해지고 → 특히 도구를 여러 개 연쇄로 호출해야 하는 경우 지금 구조로는 마지막 응답만 넘기고 있어 전체 맥락이 사라지는 문제가 있었다. 그렇다고 전체 응답을 다 넘기면 이번엔 어떤 도구를 썼는지 추적이 애매해지는 트레이드오프.

찾아본 대안은 크게 세 갈래였다. 상위에 orchestrator를 두고 여러 Tool 호출을 순차/병렬로 조합한 뒤 결과를 합치는 방식, LLM이 직접 여러 Tool 호출을 계획하고 순서를 정하는 방식(ReAct 패턴류), 그리고 Tool 내부에서 다른 Tool을 호출하는 composite Tool 방식. 각각 안정성과 자율성 사이에서 트레이드오프가 있었는데, 프로덕션에 가까운 흐름에는 orchestrator 방식이 더 맞겠다는 쪽으로 의견이 모였다. 최종적으로는 사용자 질문을 LLM에 넘겨 도구 판단만 시키고, 실제 도구 호출과 데이터 조회는 별도 계층에서 처리한 뒤 결과를 다시 LLM에 넘겨 최종 응답을 생성하는 흐름으로 정리했다.

## 그 이후

이후 팀에서 실제 서비스에 붙이면서 응답 속도와 비용 쪽을 더 다듬었다고 들었다. 초기 설계 단계에서 잡아둔 확인 절차와 응답 포맷 표준화는 그대로 유지된 채 최적화만 이어지는 모습을 보니 방향은 크게 틀리지 않았던 것 같다.
