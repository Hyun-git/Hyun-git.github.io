대규모 평가/시험 서비스를 여러 서버에 나눠 운영하다 보니, 특정 응시자가 AI 사용량을 다 써버렸을 때 그 사람의 세션을 어떻게 끊어야 하는지가 애매해졌다. 컨테이너 하나만 보고 판단하면 안 되고(한 사람이 문제를 2개 동시에 풀면 컨테이너도 2개가 뜬다), 그렇다고 무식하게 즉시 꺼버리면 채점 요청이나 마지막 저장까지 날아가버려서 이걸 어떻게 설계할지 정리하게 되었다.

### 배경

기존에는 크레딧을 다 쓰는 순간 컨테이너가 바로 강제 종료됐다. 문제는 그 시점에 채점 요청조차 못 하게 된다는 것 → 응시자 입장에서는 억울할 수밖에 없다. 그래서 하드쿼터에 도달해도 컨테이너를 바로 내리지 않고, 5분의 유예 기간을 두기로 했다. 그 5분 동안은 AI(LLM) 질문만 막고 채점 요청이나 수동 코드 수정은 계속 가능하게 두는 식.

여기서 좀 까다로웠던 부분은 AI 사용량 판정 기준이다. 한 사람이 여러 컨테이너를 갖고 있으면 그 사람이 가진 모든 컨테이너의 사용량을 합쳐서 하드쿼터 도달 여부를 판단해야 한다. 근데 사용량 API가 컨테이너(project) 단위로만 조회가 되게 만들어져 있어서, 유저 하나의 전체 사용량을 구하려면 그 유저가 가진 project 목록을 다 가져와서 N번 호출한 뒤 합산하는 수밖에 없었다.

### 무거운 판정과 가벼운 체크를 분리

이 합산 계산이 매 채팅 턴마다 도는 초고빈도 지점에서 불리면 곤란하다. 그래서 판정 자체는 LLM 호출 하나가 끝나고 크레딧이 실제로 차감되는 지점에서 딱 한 번만 수행하도록 했다. → 여기서 하드쿼터에 처음 도달했다고 확인되면, Redis Sorted Set에 `ZADD NX`로 그 유저의 `graceEndTime`(현재시각 + 5분)을 등록한다. `NX` 옵션을 쓴 이유는 재판정이 여러 번 걸려도 타이머가 계속 늘어나지 않고 최초 도달 시점 기준 정확히 5분만 유예되게 하기 위함이다.

반대로 AI 사용 자체를 막는 쪽(`checkCreditExists` 같은 공통 함수)은 매 요청마다 불리기 때문에 여기서는 무거운 합산을 다시 하지 않고, 그냥 Redis `ZSCORE`로 "이 유저가 그레이스 중인가"만 가볍게 확인하게 했다. 판정은 한 곳에서 무겁게, 소비는 여러 곳에서 가볍게 나누니까 성능 부담 없이 여러 진입점(에이전트 메시지 처리, LangGraph 노드 등)에 다 적용할 수 있었다. 5분이 지나면 스윕 워커가 20초 간격으로 만료된 유저를 찾아서 기존 컨테이너 종료 로직을 그대로 태우는 구조다.

### 150명, 300개 컨테이너로 먼저 찔러봄

설계가 끝난 다음엔 실제로 몇 명까지 감당되는지 확인해야 했다. 시험이 150명 동시 응시인데 문제를 2개(화이트박스/블랙박스) 동시에 풀게 하니 실질적으로는 컨테이너 300개를 동시에 띄워야 하는 상황이었다. `README.md 보고 풀어줘` → 후속 대화 2~3회 반복하는 시나리오로 실제 부하를 흘려봤다.

결과는 나쁘지 않았다. 150명 전원이 최소 1회 이상 완결된 응답을 받았고 유실된 사용자는 없었다. 다만 질문 단위로 보면 573건 중 514건(89.7%)만 첫 시도에 완결됐고, 나머지 10.3%는 실패했다. 근데 이게 무작위로 흩어진 게 아니라 특정 모델 그룹의 특정 5분 구간(지연이 급증한 구간)에 몰려있었던 게 흥미로웠다 → 원인이 특정되니까 타임아웃/재시도/앱 스케일링으로 표적 개선이 가능하다는 얘기가 된다. 인프라 자체 에러율은 0.585% 정도였고, 첫 토큰까지 걸리는 시간(TTFT)은 p95 기준 6.23초, LLM 단건 요청 완료는 p95 22초 나왔다. 재시도를 어느 정도 감수한다는 전제로는 150명까지도 가능하다는 결론을 냈다.

### 300 → 600 → 1,000명으로 늘려가기로

이 결과를 보고 팀에서는 다음 단계로 규모를 300명 → 600명 → 1,000명 순으로 단계적으로 늘려보기로 했다. 처음엔 API 직접 주입 기반의 모킹 부하 테스트로 서버/DB 쪽 순수 처리량을 보고, 그다음엔 실제 브라우저·LLM·컨테이너·채점 경로를 다 태우는 E2E 테스트로 넘어가는 순서였다.

내가 직접 돌린 건 그중 1,000세션 규모의 20분짜리 회차였다. 워크스페이스 1,000개, 샤드(파드) 169개를 대상으로 22.7분 동안 요청 12,278건을 보내서 11,298건이 완료됐다. 완료까지 걸린 시간은 p50 59.7초, p90 207.3초, p99 417.6초, 최대는 17분 가까이 걸린 것도 있었다. 도구 승인 대기는 p50 0초로 자동 승인이 대부분 즉시 처리됐다는 것도 확인했다.

실패율은 2.0%였는데, 원인을 파드별로 쪼개보니 두 갈래로 완전히 갈렸다. 하나는 진입 자체가 안 되는 손상된 컨테이너 3개(이전 검증 단계에서도 반복적으로 실패했던 것들이라 부하 문제가 아니라 컨테이너 자체 손상으로 판단), 다른 하나는 얼럿 팝업에 막혀서 10초 간격으로 계속 재시도하다 실패가 중복 집계된 워크스페이스 2개. 나머지 164개 파드(약 964개 대상)는 실패 0건으로 완전히 정상이었다. 시간대별로 봐도 지연이 계속 우상향하는 게 아니라 중간에 정점을 찍고 내려오는 추세라, 적어도 20분 구간에서는 메모리·컨텍스트 누적 열화 같은 건 관측되지 않았다.

회차 중에 워크스페이스 컨테이너가 한꺼번에 생기면서 클러스터 서브넷 IP가 고갈돼서 신규 노드가 못 뜨는 일이 있었는데, 이건 서브넷을 추가로 붙이고 `llm-api-server`, `ide-server` 같은 앱 파드들의 HPA min/max를 올려서 해소했다. ide-server는 회차 중 CPU가 59%까지 올라갔다가 종료 후 2%로 떨어지는 걸 보고 스케일이 맞게 잡혔다는 걸 확인했다.

그다음엔 이 흐름 그대로 더 큰 규모의 실 LLM 기반 E2E 테스트로 넘어갔는데, 그 회차 도중에는 DB 쪽에서 별도로 큰 이슈가 하나 터졌다. 그건 세션/쿼터 설계와는 결이 다른 얘기라 따로 정리해뒀다.
