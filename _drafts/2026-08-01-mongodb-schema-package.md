최근 사내 서비스 몇 개가 같은 MongoDB 인스턴스를 붙여 쓰면서 생긴 문제들을 정리하다가, 이참에 스키마 자체를 하나의 패키지로 묶어서 관리하는 작업을 진행하게 됐다. 각 서비스가 자기 코드 안에 Mongoose 스키마를 따로 선언해서 같은 컬렉션에 접근하고 있었는데, 이게 왜 문제가 되는지 처음엔 감이 잘 안 왔다. 그런데 실제로 하나씩 뜯어보니 생각보다 어긋난 부분이 많아서 정리해본다.

## 어쩌다 이렇게 됐나

서비스 A(IDE 관련 메인 서비스), 서비스 B(크레딧/결제 관련), 서비스 C(스토리지 매니저) 정도가 같은 MongoDB에 붙어 있었다. 세 서비스 다 Mongoose를 쓰긴 하는데, 각자 필요할 때마다 자기 레포에 스키마를 새로 선언해서 썼다. 처음 서비스를 나눌 때는 자연스러운 선택이었을 것 같다. 서비스 하나하나는 독립적으로 배포되니까 스키마도 각자 관리하는 게 편했을 거고.

문제는 시간이 지나면서 생긴다. `user`, `docker_info`, `project` 같은 핵심 컬렉션을 세 서비스가 동시에 건드리는데, 한쪽에서 필드를 추가하거나 이름을 바꿔도 다른 서비스는 알 방법이 없다. 코드로는 다 정상 컴파일되니까 배포도 그냥 나간다. 그러다가 실제 데이터를 조회하는 시점에 가서야 필드가 없다거나 타입이 다르다는 걸 알게 되는 식이다.

## 실제로 발견된 문제들

스키마를 감사(audit)하면서 나온 사례 몇 가지를 남겨본다.

- **컬렉션명 단복수 불일치** — `region_info`라는 이름으로 스키마를 선언한 서비스가 있었는데, 실제 DB의 컬렉션명은 `region_infos`였다. 필드 구성은 거의 같았는데 이름만 어긋나 있어서, 해당 서비스는 사실상 빈 컬렉션을 계속 조회하고 있었을 가능성이 있다. `container_run_log` / `container_run_logs`는 아예 서비스마다 다른 컬렉션명으로 선언돼 있어서 데이터가 갈라져 쌓이고 있었다.
- **인덱스 누락** — `docker_info` 컬렉션은 한 서비스에만 `uid` unique 인덱스가 걸려 있고, 나머지 서비스에서는 인덱스 없이 스키마만 선언돼 있었다. 트래픽이 늘면서 쿼리가 느려지기 시작해도, 인덱스가 없다는 사실 자체를 누구도 정확히 파악하지 못하고 있던 상태였다.
- **필드 누락/오타** — `ideNotification` 계열 컬렉션에서 한쪽 서비스 스키마에 `reportReason` 필드가 아예 빠져 있었다. `template` 컬렉션도 마찬가지로 썸네일이나 GPU 관련 필드가 일부 서비스 스키마엔 없었다. 코드만 봐서는 문제가 없어 보이니 리뷰에서도 잘 안 걸린다.
- **타입 불일치** — 어떤 필드는 Object로 다루고 있는데 실제 DB에 저장된 값은 Boolean이었던 경우도 있었다. `notification.state` 필드가 특히 그랬는데, 스키마 정의와 실제 저장값이 어긋나면서 특정 케이스에서 ValidationError가 나기도 했다.

이런 것들이 최소 열 몇 건은 나왔다. 한 건 한 건은 크게 위험해 보이지 않는데, 서비스가 늘어날수록 누적되는 게 보여서 이 상태로 계속 가면 안 되겠다 싶었다.

## 패키지로 묶기

해결 방향은 스키마 정의를 사내 npm 패키지 하나로 분리하는 것이었다. Mongoose 스키마·모델·인덱스 정의를 전부 패키지 안으로 옮기고, 각 서비스는 이 패키지를 설치해서 쓰는 구조다.

여기서 고민이 좀 됐던 부분은 서비스마다 MongoDB 커넥션을 맺는 방식이 달랐다는 점이다. 어떤 서비스는 `mongoose.createConnection()`으로 독립 커넥션을 쓰고, 어떤 서비스는 `mongoose.connect()`로 기본 커넥션을 쓴다. 후자는 `mongoose.model()`을 그대로 쓰면 되는데, 전자는 `connection.model()`을 써야 해서 패키지 쪽 모델 생성 함수가 connection을 인자로 받는 형태여야 했다.

```typescript
export function createDockerModel(conn: Connection) {
  return conn.models.docker_info || conn.model('docker_info', dockerSchema);
}
```

이렇게 팩토리 함수로 만들어두면 어떤 연결 방식을 쓰든 같은 스키마를 공유할 수 있다. 서비스 고유의 pre/post 훅이 필요한 경우엔 팩토리 함수 대신 스키마 객체만 import해서 훅을 직접 붙이는 방식도 같이 열어뒀다. 다만 같은 프로세스 안에서 같은 스키마 객체에 훅을 두 번 등록하면 훅이 중복 실행되는 문제가 있어서, 이런 경우엔 `schema.clone()`으로 격리해야 한다는 걸 나중에야 알게 됐다.

## 배포 파이프라인

인덱스 변경 이력을 코드로 관리하기 위해 migrate-mongo를 붙였고, `develop` → `main` PR이 머지되면 GitHub Actions가 빌드하고 패키지 레지스트리에 자동 배포하도록 구성했다. 브랜치 보호 규칙 때문에 `main`에 직접 push는 막혀 있어서 반드시 PR을 거쳐야 한다.

버전은 한 번에 다 고치지 않고 여러 차례 순차적으로 올렸다. 초기 버전에서 컬렉션명 단복수부터 바로잡고, 그다음 버전에서 인덱스를 하나씩 보강하고, 그 이후에 스키마 전체를 다시 감사해서 누락된 필드나 enum, default 값을 복구하고, 마지막으로 여러 서비스가 공통으로 쓰는 모델을 shared 영역으로 옮기는 식이었다. 한 번에 다 뜯어고치려 했으면 리뷰하기도 어려웠을 것 같고, 실제로 나눠서 배포하니 문제가 생겨도 어느 버전에서 뭐가 바뀌었는지 추적하기가 훨씬 쉬웠다.

## 자잘하게 겪은 것들

패키지를 실제로 서비스에 적용하는 과정에서 스키마 문제보다 오히려 이런 부수적인 것들 때문에 더 시간을 썼던 것 같다.

레지스트리 캐시가 안 갱신되는 문제가 있었다. 새 버전을 배포했는데도 사내 프록시 레지스트리가 이전 버전의 메타데이터를 캐시하고 있어서, 브라우저로 버전이 보이는데도 설치는 실패하는 경우였다. 이건 결국 캐시 무효화를 요청해야 풀렸다.

`package-lock.json`의 `resolved` URL이 예전 레지스트리 주소로 고정되면서 CI에서 401 인증 에러가 나기도 했다. lockfile에 박힌 URL이 실제로 지금 쓰는 레지스트리와 다르면 로컬에서는 캐시 덕분에 잘 되다가 CI에서만 터지는 경우가 있어서, 원인 찾는 데 좀 걸렸다.

그리고 로컬 npm 버전과 Docker 이미지의 npm 버전이 달라서 peer dependency 해석 방식이 갈리는 바람에 `npm ci`가 실패한 적도 있었다. 로컬은 npm 11이라 문제없이 지나가는데 Docker는 npm 10이라 lockfile에 없는 의존성을 요구하는 식이었다. `.npmrc`에 `legacy-peer-deps=true`를 넣는 걸로 일단 우회했다.

스키마를 하나로 모으는 것 자체는 방향이 명확했는데, 막상 실무에 붙이려니 이런 인프라성 이슈들이 더 까다로웠던 것 같다. 그래도 지금은 스키마가 어디서 어떻게 정의되는지 한곳에서 확인할 수 있게 됐고, 새로 컬렉션을 추가할 때도 같은 패턴을 따라가면 되니 확실히 나아진 것 같다.
