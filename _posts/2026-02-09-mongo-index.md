---
title: MongoDB 인덱스 정리하다가 알게 된 복합 인덱스와 prefix rule
layout: post
---

최근에 MongoDB 인덱스 리뷰를 받다가 아래와 같은 코멘트를 받았다.
> “이 인덱스 중복 아닌가요?”

처음엔 솔직히 잘 와닿지 않았다. 인덱스는 많을수록 좋은 거라고 막연히 생각하고 있었기 때문이다.

근데 실제로 하나씩 뜯어보니, 내가 마주한 상황은 꽤 전형적인 실수 케이스였다.

내가 만든 인덱스 상태 대략 이런 인덱스들이 있었다.
```ts
{ userId: 1 }
{ userId: 1, isActive: 1 }
{ userId: 1, inviteeUsers.userId: 1, inviteeUsers.firstPurchase: 1 }
```

겉으로 보면 딱히 이상 없어 보인다.
근데 문제는 이미 복합 인덱스가 있는데도 single 인덱스가 같이 존재하고 있었다는 점이다.

복합 인덱스가 있는데 single 인덱스가 왜 필요 없을까?

MongoDB에는 prefix rule이라는 게 있다.

복합 인덱스가

{ userId: 1, isActive: 1 }


이렇게 생겼다면, MongoDB는 아래 쿼리들을 전부 이 인덱스로 처리할 수 있다.

{ userId: "u1" }
{ userId: "u1", isActive: true }


즉,

{ userId: 1 }


이 single 인덱스는
이미 복합 인덱스에 포함된 prefix라서 역할이 겹친다.

이걸 모르고 있으면
“혹시 몰라서” 인덱스를 계속 추가하게 된다.

결과는
👉 중복 인덱스 + 쓰기 성능 저하 + 관리 포인트 증가

그럼 single 인덱스는 언제 의미가 있을까?

내가 정리한 기준은 이거다.

복합 인덱스가 아예 없을 때

복합 인덱스의 첫 필드가 아닐 때

그 외에는 대부분
복합 인덱스 하나로 충분한 경우가 많다.

index: true가 만든 사고

이번 케이스에서 더 문제였던 건 이거였다.

@Prop({ index: true })
userId: string;


이 한 줄 때문에
MongoDB는 자동으로 { userId: 1 } 인덱스를 만들어버린다.

그 상태에서 schema 레벨에서 복합 인덱스를 추가하면
의도치 않게 중복 인덱스 세트가 완성된다.

이후로는 규칙을 하나 정했다.

필드 단위 index: true는 거의 쓰지 않는다.

인덱스는 schema-level에서만 명시적으로 관리하는 게 훨씬 안전했다.

unique 인덱스는 예외다

다만 하나 예외가 있다.

{ code: 1, unique: true }


이건 무조건 인덱스가 필요하다.

MongoDB에서 unique 제약은
인덱스를 통해서만 보장된다.

그래서 unique 조건이 들어간 필드는
“이게 조회에 쓰이냐?”와 상관없이
인덱스를 가져가는 게 맞다.

정리하면서 세운 기준

이번에 인덱스를 정리하면서 기준을 이렇게 잡았다.

복합 인덱스가 있으면 prefix single 인덱스는 제거

index: true는 최대한 사용하지 않기

인덱스는 schema-level에서만 정의

unique는 예외 없이 인덱스 유지

한 줄 결론

복합 인덱스를 만들었다면
그 prefix에 해당하는 single 인덱스는 대부분 필요 없다.

이번 리뷰 덕분에
“인덱스를 많이 거는 것”보다
“의도를 명확히 하는 것”이 훨씬 중요하다는 걸 배웠다.

다음에 또 비슷한 인덱스를 추가하려고 할 때,
한 번쯤은 getIndexes()부터 열어보게 될 것 같다.
